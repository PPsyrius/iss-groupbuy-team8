# Deployment operations

Use the [backend EC2 operator guide](../../../docs/deploy/backend-ec2-pipeline-operator-guide.md), [dev CloudFront runbook](../../../docs/deploy/dev-cloudfront-deployment.md), [backend runtime bundle](../../../deployment/backend/README.md), and [production operations runbook](../../../docs/deploy/prod/backend-prod-operations-runbook.md) for commands and current deployment design. This skill is a verification checklist, not a second source of cloud configuration.

## Establish the actual state

- Read `git status --short --branch`, the branch diff, the relevant workflow and its runbook before attributing a change to a PR. Distinguish local edits, pushed branches, merged `dev`, deployed image/artifact and checks made against the live site. A green workflow for an older SHA is not verification of the current branch.
- Verify the AWS account, Region, target instance or distribution, GitHub environment, deploy switch and role before a cloud operation; do not infer live settings from checked-in examples. The dev runbooks target account `402178232802` in `ap-southeast-1`, but confirm the current target in AWS/GitHub. If `gh` or AWS CLI is unavailable, report what was not checked rather than treating a board snapshot or runbook as live state.
- An AWS Organizations SCP explicit deny is not fixed by expanding a local IAM role. Check the Region and the denied action before diagnosing access; Session Manager's optional session document can remain blank for a shell, while `AWS-StartSSHSession` is a port session and is not the console shell. Use a documented alternative only if its permissions are available.

## Keep controls in the right place

- GitHub Actions variables such as `ENABLE_EC2_DEPLOY` and `ENABLE_S3_DEPLOY` gate workflows; they are not automatically container environment variables. Follow the workflow when deciding whether a variable belongs to the repository or a protected environment. Confirm `backend-dev` and `frontend-dev` allow only `dev`, and verify the immutable OIDC subject and scoped role policy before changing trust.
- Prod `backend-prod-publish` and `backend-prod` allow `v*` tags only. This private repository has no native reviewer gate: `ENABLE_EC2_DEPLOY_PROD` must stay unset/false until an operator explicitly authorizes release readiness. Manual prod rollback must dispatch from an existing release tag (whose commit includes the tag-ref guard), not `dev`; automatic rollback during a failed deploy is separate and unchanged. Verify both environment policies before any tag.
- Dev backend runtime settings live in `/etc/blocbuy/backend.env` on EC2 (`root:root 0600`), consumed by `deployment/backend/compose.yml`. The dev deploy workflow does not render that file. Production `bin/fetch-env.sh` instead recreates it from `/blocbuy/prod/*` SSM parameters; seed newly required keys, including `BLOCBUY_SCHEDULING_ENABLED=false`, before a production release.
- A container restart retains its old environment. After changing the host env file (and fetching SSM values first in prod), use the reviewed deployment path that force-recreates the backend service; verify the resulting container value without printing unrelated variables. Count overdue open teams before explicitly enabling an expiry scheduler, and distinguish durable refund obligations from an active refund worker.
- Never ask for or display an entire runtime env file, token, policy secret or decrypted SSM response as verification. Check only the needed non-secret key, permissions, health or redacted metadata. If a real credential is exposed, do not repeat it; coordinate rotation with the owning service and host configuration.
- Viewer HTTPS does not encrypt a `http-only` CloudFront→ALB origin; prefix-list SG and `X-Origin-Secret` restrict access, not observation. Revoke an exposed value with an authorized dual-value ALB/CloudFront rotation, then require a reviewed regional-certificate/HTTPS-origin cutover and another rotation for transit confidentiality (NFR-37). Neither belongs in a no-op Terraform import.

## Terraform state adoption

- Distinguish declared config, offline validation, remote init, import-only plan, applied state import, post-import `plan -detailed-exitcode` exit 0 and merged PR; none alone proves the others. [`infra/terraform/README.md`](../../../infra/terraform/README.md) owns stack/state boundaries; the [frontend stack guide](../../../infra/terraform/frontend-stack/README.md) owns drift checks. The dev ALB remains outside frontend-stack.
- With existing resources, review a saved plan for imports only and zero create/update/delete actions before an authorized apply; afterward require exit 0 from a fresh detailed-exitcode plan against the same account and private variables. DynamoDB backend locking is deprecated in Terraform 1.16 but remains the configured lock for these stacks; a backend migration is a separate change. Keep provider lockfiles distinct from CLI version constraints, and never claim a state import or PR merge from an offline validation.
- CloudFront AWS provider 5.100.0 treats `origin` as a set: a sensitive mark on a custom-header value can cause a false whole-origin diff even when before/after fields match. Any approved `nonsensitive` at the provider boundary retains declarative origin management but makes raw plan/state and changed-header diffs secret-bearing; never request, paste or attach a full plan. Keep any private saved plan/log access-restricted in the operator workspace and remove it after recording filtered resource addresses/actions; if a value escapes, coordinate rotation without repeating it.
- Compare a CloudFront Function's DEVELOPMENT and LIVE code with the versioned source when importing, especially after a Windows ZIP transfer (CRLF changes function bytes). The provider's `publish` argument defaults to true but is not refreshed on import; avoid an unreviewed publish, and document who publishes future LIVE changes. Preserve the exact verified HCL and provider lockfile until a human PR lands when the import was executed from an uncommitted copy.
- Resolve CloudFront's origin-facing prefix list with `aws_ec2_managed_prefix_list`, not legacy `aws_prefix_list`; verify the AWS-owned ID in the target Region. Under CloudShell storage pressure, reuse a previously signed provider binary only after byte comparison and `init -lockfile=readonly`; filesystem mirrors report `unauthenticated` without signature metadata.
- For origin-secret rotation, compare private values, admit old/new at the ALB, review a CloudFront-only plan, wait for `Deployed` and API health, remove the old ALB match, then require plan exit 0. A computed distribution ARN can spuriously update S3/IAM policies; review a stable ARN and an old-value zero-change baseline first. Keep rollback conditions, plans and logs private.
- When `trivy-config` uses SARIF output, an exit code 1 may show no findings in the job log: inspect the uploaded SARIF artifact for rule ID and resource before changing IaC. Prefer fixing a real misconfiguration; when importing an unchanged resource makes the live change out of scope, add a resource-scoped `tfsec:ignore` with a concrete reason, record the exception in the NFR/log evidence, and rerun the pinned Trivy version with HIGH/CRITICAL severity. Do not disable the global gate.

## Verify the delivered behavior

- For frontend delivery, match the packaged commit to the S3/CloudFront deployment run, check root, deep link, immutable asset and API health, and compare exact root and `/api/*` security-header name/value pairs with the checked-in policy. Distinguish a passed smoke test from unseeded authenticated flows.
- For backend delivery, confirm the immutable ECR digest, SSM command outcome, EC2-local and public health, runtime profile and the expected container setting. Application rollback does not reverse a Flyway migration; review migration compatibility before enabling automatic deploy.
- Do not call an edge Terraform-managed merely because resources or declarations exist. The dev frontend met the reviewed import and zero-change-plan gate on 2026-09-25, but its source still needs a merged PR; verify the current state and branch before attributing that result to checked-in `dev`. The dev backend EC2/ALB remains hand-managed.
- Record command or workflow link, SHA/digest, target, observed result, limitations and owner in the sprint log and relevant NFR row via [agile-evidence-capture](../agile-evidence-capture/SKILL.md). Do not rewrite historical snapshots or close issues merely because a deployment command was attempted.
