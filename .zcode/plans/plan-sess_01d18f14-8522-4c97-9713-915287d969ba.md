## 构造方法(为什么不是 cherry-pick)

每层:基于上一层 `git switch -c split/NN`,然后按**文件归属清单**(已从 diff 数据导出)从对应边界 commit `git checkout <commit> -- <paths>` 或 `git diff A B -- <paths> | git apply`,提交。理由:

1. order 与 payment 在 `c84868d` 之后交织,不存在干净的 cherry-pick 顺序;
2. 共享文件(`OrderErrorCode`、`StripeLocalIntegrationTest`、`OrderControllerTest`、nfr-register)在三层各有**正确的中间状态**,树构造天然得到,cherry-pick 需手工剥离;
3. merge 夹带的契约脚本只有树构造能带上;
4. squash-merge 落地,无历史损失。

**证据处理**:A 落地历史日志(记录性质,先于代码合入);B/C/D 各自向当天日志文件追加一条指向自己 PR 的新条目(满足规则向前生效)。

| 层 | 构造 | 本地验证 | CI 墙钟 | 描述+证据 | 主要风险 | 难度 |
|---|---|---|---|---|---|---|

| B | 0.5h | 0.5–1h | 20–30min | 0.5h | 中间树从未独立过 CI;contract-check | 中低 |

栈管理(retarget/rebase,每次下层合并后):4 × 0.25h。**净工作 6–8h;加 ~40% 应急(中间树编译/测试意外、sonar 门禁失败)→ 8–11h**,跨 2–3 个工作日,主导因素是评审响应速度。本地验证需要 Docker 跑 Testcontainers。

时间线:A+B 第一天构造发出 → C 随 A/B 合并发出 → D 最后。全部合并后关闭 #125,并把 #125 已有 review 意见逐条核对迁移到对应新 PR。

## 风险清单

1. **中间树从未独立跑过 CI**(f3d1f4f/d1c9d7e 虽是历史 HEAD,应绿,但减去 docs 后是新树)→ 缓解:每个 PR 发出前本地 `./mvnw verify` 全量通过;应急预算已含。
2. **迁移号竞态**:栈在飞期间他人向 dev 合入新 V12+ 会撞号 → 在当天日志声明 V12–V16 已被本栈占用,并尽快合并。
3. **#125 的存量 review**:执行第 0 步先 `gh pr view 125` 查 review/评论(本次规划中该查询被沙箱拦截,未确认),有实质意见则逐条迁移。
4. sonar 对每个 PR 独立算覆盖率门禁,三层各自带足测试,预计能过,失败归入应急。
5. docx 二进制若团队不想进 git,从 A 中单独挪出(5 分钟,不阻塞)。

## 被否决的替代方案

- **最小拆分**(只拆 A,代码仍是一个 8.5k 行 PR):约 2h,解决日志碰撞,但评审质量问题原样保留。
- **不拆**,仅在 PR 描述给评审指南:约 1h,评审质量最差。
- 全栈拆分的增量成本(约 6–10h)买到的:payment/退款这一最高风险代码获得真实评审、冲突面缩小、证据规则合规。
