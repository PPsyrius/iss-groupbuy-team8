# Splitting PR #125: execution plan for four stacked PRs

## Verified facts

- **PR #125 exists and is OPEN** (head = `feature/order-deal-20260919`). It touches 126 files, +10,259/−833; the backend accounts for 100 files and +7,749, of which about 4,200 lines are tests.
- **The branch history has two clean tree boundaries**:
  - `f3d1f4f` = order core complete, payment integration not started (and that day's `dev` already merged in);
  - `d1c9d7e` = payment/purchase-intent integration complete, lifecycle not started.
- **Flyway migrations layer naturally**: `dev` currently ends at V11. This branch adds V12__order and V13__scheduler_lock (→ layer B), V14__product_team_terms and V15__purchase_intent (→ layer C), and V16__refund_due_index (→ layer D). Merged in stack order, each step keeps version numbers strictly increasing, which Flyway accepts.
- **A merge commit carries a hidden change**: the change to `scripts/check-stripe-dev-contracts.py` (+38/−7) exists only in a merge commit's conflict resolution; no regular commit touches it. **A cherry-pick approach would silently drop it, so the branches must be built from tree states.**
- **CI reality** (this sets the verification cost of each layer): a backend PR must pass `build-quality` (Spotless/Checkstyle + `mvn verify`, including every `*IT` on Testcontainers PostgreSQL), `contract-check` (regenerates `openapi.json` and fails on any drift), Sonar, the Docker smoke test and Gitleaks. The repository squash-merges, so a source branch's intermediate commits are not kept after landing; building from trees loses no history of value.
- **Evidence rules**: every code PR carries its own sprint-log entry for the day. NFR-27..29 belong to the payment layer and NFR-30/31 to the lifecycle layer; ADR 0001 goes with C, ADR 0002 with D.

**Completeness invariant**: once D is built, `git diff split/04-lifecycle-refund feature/order-deal-20260919` must be empty. This proves that none of the 126 files is missing and that no hidden change was lost. The original branch stays untouched as a backup and reference.

## Construction method (why not cherry-pick)

For each layer: `git switch -c split/NN` from the previous layer, then, following the **file ownership list** (already derived from the diff data), take the files from the matching boundary commit with `git checkout <commit> -- <paths>` or `git diff A B -- <paths> | git apply`, and commit. Reasons:

1. Order and payment interleave after `c84868d`, so no clean cherry-pick order exists.
2. Shared files (`OrderErrorCode`, `StripeLocalIntegrationTest`, `OrderControllerTest`, the NFR register) each have a **correct intermediate state** in three layers. Building from trees yields those states directly; cherry-picking would need manual stripping.
3. Only tree construction carries the contract script hidden in the merge commit.
4. Squash-merge landing means no history is lost.

**Evidence handling**: A lands the historical logs (a record, merged before the code). B, C and D each append a new entry to the day's log file that points to their own PR, so the rule holds from here on.

Local verification needs Docker for Testcontainers.

Timeline: build and open A and B on day one → open C as A/B merge → D last. Once everything is merged, close #125 and move each existing #125 review comment to the matching new PR.

## Risks

1. **The intermediate trees have never run CI on their own** (`f3d1f4f`/`d1c9d7e` were real HEADs and should be green, but minus the docs they are new trees) → mitigation: a full local `./mvnw verify` passes before each PR is opened; the contingency covers it.
2. **Migration number race**: if someone merges a new V12+ into `dev` while the stack is in flight, the numbers collide → state in the day's log that V12–V16 are reserved by this stack, and merge quickly.
3. **Existing #125 reviews**: step 0 runs `gh pr view 125` to read reviews and comments (the sandbox blocked this query while planning, so it is unconfirmed); any substantive comment is moved over one by one.
4. Sonar computes the coverage gate per PR; each layer carries enough tests of its own and is expected to pass; a failure is covered by the contingency.
5. If the team does not want the docx binary in git, move it out of A separately (5 minutes, not blocking).

## Rejected alternatives

- **Minimal split** (split out A only; the code stays one 8.5k-line PR): about 2h. It solves the log collisions but leaves the review-quality problem as it is.
- **No split**, only a reviewer guide in the PR description: about 1h; the worst review quality.
- What the extra cost of the full stacked split (about 6–10h) buys: real review of the payment/refund code, which carries the highest risk; a smaller conflict surface; compliance with the evidence rules.

## Execution steps after approval

1. Check the #125 review status; push the current branch to origin as a backup (if not pushed yet).
2. Build and open A (base: `dev`).
3. Build B (base: the A branch, so review sees only this layer's diff); open it once a local `./mvnw verify` passes.
4. While waiting for merges, build C and D and verify each.
5. After each lower layer merges, retarget the next layer's base to `dev`; finally run the completeness invariant check; close #125.
6. Each code PR carries the day's log entry; each PR description includes a "reviewer guide for this layer" (topic, entry classes, verification commands).

Do not modify `feature/order-deal-20260919` itself; do not touch `dev`; do not force-push any remote branch.
