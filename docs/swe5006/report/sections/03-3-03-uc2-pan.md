### 3.3.3 UC2 Register and Authenticate

A visitor signs in with their Google account; on the first sign-in BlocBuy registers them as a buyer, and on every sign-in it opens a session so that they can start and join teams and see their own orders. Google is the only sign-in channel, as the proposal planned, so BlocBuy stores no passwords.

**Actors:** Buyer or Admin (primary; a visitor who is not yet signed in). Google (secondary; verifies the identity).

**Preconditions:** The visitor has a Google account. BlocBuy is registered with Google as a sign-in client.

**Trigger:** The visitor presses "Continue with Google", or tries an action that needs a session: starting or joining a team, opening the account page or the admin console.

**Normal flow:**

1. When the action came from a listing, the system first shows a sign-in sheet that explains why a session is needed; the visitor chooses to sign in. The system remembers the page to return to.
2. The system issues a one-time sign-in state, binds it to the browser, and redirects the browser to Google's consent page.
3. The visitor signs in at Google and consents.
4. Google redirects back to BlocBuy with an authorisation code and the state.
5. The system consumes the state, which must match the browser's binding and must not have been used before.
6. The system exchanges the code with Google and verifies the identity that Google returns.
7. The system looks up the account bound to this Google identity. If none exists, it registers one: the account, the Google binding and the default *buyer* role. If one exists, it records the sign-in time.
8. The system checks that the account is active and opens a session for the browser.
9. The browser lands on the sign-in callback page, which reads the current user and returns the visitor to the page remembered in step 1.

**Alternative flow, sign out:**

- 9a. A signed-in user chooses "Sign out". The system ends the session and the page shows the anonymous header with a sign-in link.

**Exceptional flows:**

- 3a. The visitor cancels or denies consent at Google: the system opens no session and shows the sign-in page with an "access denied" error and a retry button.
- 5a. The state is missing, already used, or does not match the browser's binding (for example a replayed or forged callback): the system rejects the callback, opens no session and shows the sign-in error page.
- 6a. Google is unreachable, or the code or token cannot be verified: the system opens no session and shows the sign-in error page.
- 7a. Two first sign-ins of the same Google identity race: one registration wins; the other re-reads the binding and signs in to the same account.
- 7b. Another local account already uses the same e-mail address: the system refuses to merge the two accounts and opens no session.
- 8a. The account is disabled: the system refuses the sign-in and opens no session.
- 9b. The callback page finds no session (the browser did not keep it): it shows the sign-in error page.
- A1. At any later time, a request without a valid session to a protected operation is refused as not signed in. The page then treats the visitor as anonymous; a protected page redirects to the sign-in page and returns afterwards.
- A2. A signed-in buyer without the admin role calls an admin operation: the system refuses it, and the admin console shows "Access denied". The admin role is granted by an operator in the database; no screen grants it.

**Postconditions:** On success, exactly one active local account is bound to the Google identity, new accounts hold the buyer role only, and the browser holds a session for that account. On any failure, no session exists and no two accounts have been merged.

**Analysis objects:** sign-in page and callback page «boundary»; Google identity provider (secondary actor reached through a «boundary»); sign-in control «control»; account, Google identity binding, role and sign-in state «entity».
