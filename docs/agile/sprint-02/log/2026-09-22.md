## 2026-09-22 - l0sgAi (Liu Jin) - Order fulfilment adapter: the payment business port gets its production half (#124, #126)

- Kind: feature (PR-C). `OrderFulfilmentAdapter` implements all six `PaymentBusinessPort` methods, so the contract whose Javadoc still read "No production stub is supplied" now has one.
- Changed: the lock order is global and unchanged — group deal → purchase intent → payment, and every method takes the team lock first. `GroupDealSettlementSupport` is the third facade: it locks the team, backfills `biz_group_member.order_id` and reads a membership by payment, and it only locks, never judges, because at settlement a team may legitimately be full, succeeded or expired and deciding that belongs to `PaidGroupDealService` once the money is presented. `PaidGroupDealRepository` gains `linkOrder` and `findPaidMember`; `PaidMember` is the new value object. Order and deal numbers are derived from the payment or deal id — prefix, UTC day, and the UUID's low 12 hex digits — rather than drawn from a sequence, so a replayed fulfilment cannot invent a second number for the same fact.
- Decisions: an `Outcome` carrying a rejection is committed by the caller, which then arranges a refund, so a rejection returned after a write would commit that write alongside the refund. Every rejecting check — already fulfilled, buyer inactive, product unsellable — is therefore read-only and runs before the first write; after that point failures throw and roll the settlement back, including losing the last unit at `consumeOneUnit`, where the webhook retries and the purchasability check refuses it cleanly. `fulfilmentEvidence` no longer checks order status the way the fixture's `o.status='paid'` did: a real order is created PENDING and moves with the team's lifecycle, none of which unmakes the fulfilment, so it cross-checks the member, the order and the intent instead.
- Verified: JDK 21 `./mvnw -B verify` BUILD SUCCESS. New: `OrderFulfilmentAdapterTest` 37, `GroupDealSettlementSupportImplTest` 12, plus additions to the groupbuy persistence and `ParticipationResult` suites. JaCoCo aggregate: no missed line or branch in any file touched. Contract unchanged.
- Problems: `PaidGroupDealService` locks its receipt before the deal, so the combined path is team → intent → receipt → team and is a cycle on paper. It cannot deadlock in practice because a receipt is keyed by payment id and no two transactions contend for the same one; PR-D owes the concurrency IT that demonstrates this.

- Changed (PR-F, #132 and #133): `processNext` splits a single `catch (BizException)` into permanent (`PAYMENT_STATE_INVALID` → `review` / `PROVIDER_STATE_MISMATCH`) and transient (`PAYMENT_PROVIDER_ERROR` → `processing` / `PROVIDER_RETRY`), so a non-refundable PaymentIntent no longer costs a provider call every 30 seconds for 23 hours. `reconcile` splits the same way but keeps the stored state at `review` either way, because that row is in an operator's hands and handing it back to the automatic worker mid-investigation is not an improvement. `claimNext` no longer claims `succeeded`, `finish` no longer schedules a next attempt an hour out, and `V16__refund_due_index.sql` narrows the partial index to match — DROP and CREATE without `CONCURRENTLY`, since Flyway runs migrations in a transaction and the table is tiny.
- Changed (PR-J #139, and PR-I): a webhook whose `payment_id` is not a UUID, or which names a payment this database has never held, is now an ignored event — recorded as `UNKNOWN_PAYMENT` and acknowledged 2xx, touching neither `business`, `lock` nor `save`.
