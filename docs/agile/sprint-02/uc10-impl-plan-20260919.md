## 2. PR-1 — migrations + ports + contract (planned for 15 Sep)

### 2.1 V9__order.sql

Promote `docs/db/order.sql` into
`backend/blocbuy-bootstrap/src/main/resources/db/migration/`, adding two guarantees (plan §3.2.3):

```sql
-- New column on top of docs/db/order.sql: the payment deduplication key.
-- In practice this is a column in the CREATE TABLE statement:
    payment_id     uuid,   -- the payment that produced this order; replayed confirmations collide in the database
-- New indexes (inside the same migration):
CREATE UNIQUE INDEX uq_biz_order_payment_id
    ON biz_order (payment_id)
    WHERE deleted = false AND payment_id IS NOT NULL;
CREATE UNIQUE INDEX uq_biz_order_deal_user
    ON biz_order (deal_id, user_id)
    WHERE deleted = false AND deal_id IS NOT NULL;
```

Key points:

- carry over every column and comment from `docs/db/order.sql` verbatim, do not redesign; add only
  `payment_id` and the two partial unique indexes
- no FK, no CHECK (the conventions forbid them); `status` stays `varchar(16)` validated by the
  application
- the status vocabulary is fixed: `pending → confirmed | cancelled` (lowercase, matching the
  existing `biz_payment` comment style); update the doc comments to match

## 3. PR-2 — behaviour on the Order aggregate (planned for 16 Sep; the Payment aggregate is Yorik's)

### 3.1 OrderStatus / Order

`com.blocbuy.order.model.OrderStatus`: enum `PENDING, CONFIRMED, CANCELLED` plus a
`canTransitionTo` check (the state machine is cohesive; services must never branch on status with
if/else).

`Order` fields: `id, orderNo, paymentId (deduplication key, sourced from the id of Yorik's Payment
aggregate), dealId (Optional), userId, productId, productTitle, productImage, quantity, unitPrice
(BigDecimal), totalAmount, currency, status, paidTime, cancelTime, version`.

Behaviour (replacing the current placeholder, keeping the "born valid" factory style):

```java
public static Order create(...)                 // factory: validates amount > 0, quantity > 0, totalAmount = quantity * unitPrice
public Order confirm(Instant now)               // PENDING → CONFIRMED; otherwise BizException(OrderErrorCode.ORDER_ILLEGAL_TRANSITION)
public Order cancel(String reason, Instant now) // PENDING → CANCELLED; stamps cancelTime
public Order reconstitute(...)                  // for repository reconstruction; package-private or same package
```

- money does not reuse `GroupDealMoney` (an aggregate internal to the groupbuy package; cross-domain
  access would be a violation) → plain `BigDecimal` plus a `currency` field
- the snapshot fields `productTitle` / `productImage` are persisted, so editing a product later does
  not rewrite history (a UC9 risk)
- no `setStatus`, no `@Data`; immutable style, a transition returns a new state snapshot or mutates
  internally, following the `GroupDeal.joinPaid` convention
- `Order` references only `paymentId` (a UUID) and never imports the Payment aggregate → zero
  compile coupling with Yorik's work

Add the missing `OrderErrorCode` values: illegal transition, order not found, concurrent conflict
(or hang it on `CommonErrorCode.CONFLICT` — check the existing enum first and add only what is
missing). No free-form string exceptions.

## 4. PR-3 — Order persistence slice + ITs (planned for 17 Sep; the payment slice is Yorik's)

Following the four-piece `catalog/persistence` pattern:

```
infrastructure/order/persistence/   BizOrderDO, BizOrderMapper, OrderConverter, OrderRepositoryImpl
```

- hand-written DO↔domain converter, no MapStruct; DOs never leave infrastructure (the ArchUnit rule
  `persistence_is_internal` must stay green)
- `saveIfVersion`: `UPDATE ... WHERE id=? AND version=?` → 0 affected rows means a conflict → throw
  `BizException(CONFLICT)` → the global handler answers 409 (US20 AC: an optimistic conflict shows
  as 409 rather than a lost update)
- `confirmByDealId` / `cancelByDealId`: status-guarded UPDATE (`WHERE deal_id=? AND
  status='pending'`), so an idempotent replay affects 0 rows and is a no-op — the 22 Sep
  `OrderConfirmationSubscriber` consumes these directly
- `update_time` / `update_by` are maintained by the application (the database does not update them
  automatically); no Mapper calls inside loops (this slice has none — MyBatis issues one batch
  statement)
- ITs (Testcontainers, following the `PaidGroupDealRepositoryIT` template):
  - `OrderRepositoryIT`: save/findById/findByPaymentId, a `uq_biz_order_payment_id` collision, a
    `uq_biz_order_deal_user` collision, a `saveIfVersion` conflict, `confirmByDealId` idempotence
    (run twice; the second run affects 0 rows)
  - run both paths, "empty database" and "Sprint 1 database" (V9 applies cleanly to an already
    populated database — a US20 AC; verify with a Testcontainers image pinned at V8, or an init
    script)

## 6. Application-layer obligations (the database does not enforce these; the code must)

- legal `status` values and the referential validity of `deal_id` / `user_id` / `payment_id` →
  validated by the application
- `total_amount = quantity × unit_price` computed by the application before insert
- `update_time` / `update_by` maintained by the application
- scheduler lock: `SELECT ... FOR UPDATE NOWAIT`, and skip the run when it cannot be acquired
  (consumed by Pan)
- the participating transaction is one unit of work covering receipt + member + order (lands 22 Sep
  with Eric's `GroupDealParticipationHandler`); Stripe calls are forbidden inside a transaction
  (per the conventions)
