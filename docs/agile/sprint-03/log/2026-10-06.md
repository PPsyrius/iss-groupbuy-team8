- Kind: SWE5001 DevSecOps verification and IAM fix; [#376](https://github.com/PPsyrius/iss-groupbuy-team8/issues/376), branch `fix/swe5001-apply-role-gaps-20261006`.
- Promotion [#408](https://github.com/PPsyrius/iss-groupbuy-team8/pull/408) (merge commit `7e1407b9`), [run 37433511513](https://github.com/PPsyrius/iss-groupbuy-team8/actions/runs/37433511513): `images` and `publish` passed; `up` planned 71 runtime resources and created 59 (VPC, subnets and routes, security groups, ALB with listener, rules and target group, RDS with subnet and parameter groups, Valkey, ECS cluster and capacity providers, Cloud Map namespace, IAM roles under the permissions boundary, log groups, fck-nat launch template, ENI and EIP), then failed; `release` was skipped; `down` failed before destroying anything; `evidence` passed.
- Cause 1: the apply role had no `ssm:DescribeParameters`, which has no resource-level permission, so the provider could not read the metadata of `shared/REDIS_PASSWORD`, `shared/DB_MASTER_PASSWORD`, `monolith/DB_OWNER_PASSWORD` and `monolith/DB_APP_PASSWORD`. It failed `up` and, during the refresh, `down`.
- Cause 2: the guardrail `DenyChangesOutsideSwe5001` (resources `*`, deny unless `aws:ResourceTag/Course = swe5001`) listed the security group rule actions. AWS also authorises them against the new `security-group-rule/*` resource, which is untagged at creation, so the explicit deny matched `alb_from_cloudfront`, `dbinit_to_rds`, `dbinit_to_https`, both `nat_from_private` rules and `nat_to_internet`.
- Cause 3 (no code change): the fck-nat ASG reported `Authentication Failure`. `AWSServiceRoleForAutoScaling` was created at 2026-10-06T08:08:07Z, 2 s after the ASG create, because this was the account's first Auto Scaling group; the ASG's later activity was `Successful`, so the failure was service-linked-role propagation.
- Teardown: the leftovers (RDS, Valkey, ALB, EIP, the NAT instance the ASG launched later, ECS cluster, namespace, VPC) needed an admin: an operator ran `env-down.sh` in CloudShell, whose credentials include `DescribeParameters`.
- Changed: `foundation` adds an allow for `ssm:DescribeParameters` on `*` (metadata only, never a value) and moves the five security group rule actions into a new deny, `DenyRuleChangesOutsideSwe5001`, scoped to `security-group/*` with the same tag condition, so rules on the untagged SWE5006 groups stay denied. New mocked-provider test `tests/apply_policy.tftest.hcl` asserts both.
- Audit of the next resources: no further clear gap. ECS task definitions and the service fall under `AmazonECS_FullAccess` and the `ecs-tasks` pass-role rule; ECS registers targets through its service-linked role; RDS and ElastiCache denies are already limited to instance, cluster, replication-group, snapshot and backup ARNs; no CloudWatch alarm, SNS or SQS is in the monolith topology. Uncertain until a run: the `edge` refresh reads by the apply role (S3 bucket subresources and `UpdateDistribution` under its tag condition), the first ECS `CreateService` with Service Connect, and db-init reaching RDS.
- Verified locally: Terraform 1.16.4 `fmt -check`, `validate` for `foundation`, `runtime` and `edge`; `terraform test` for `foundation` 4 passed, 0 failed; the new test fails all three assertions against the previous policy; `git diff --check` clean.
