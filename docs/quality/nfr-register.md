# Non-Functional Requirements Register

Measurable scenarios, controls and evidence. Gate thresholds: [quality-gates.md](quality-gates.md).

Each row answers four questions: what do we require, how is it controlled, what evidence do we have, and what is still unverified? Follow the evidence links for test output and history. Local tests do not establish deployed behavior.

- `enforced`: an automated or runtime check rejects violations.
- `implemented`: the control exists and has been verified in code or configuration.
- `measured`: an actual result has been recorded.
- `unmet`: the requirement currently fails.
- `documented`: the approach is agreed but not verified.
- `accepted-risk`: an owner approved an exception until a stated date.
- `target undefined`: no measurable target has been agreed.

Keep requirements, controls and remaining gaps in this register; keep detailed chronology in linked records. GitHub tracks merges and release records track deployment. Scenario guidance: `.claude/skills/agile-evidence-capture/references/nfr-scenarios.md`.

## PR validation convention — 2026-10-21

This convention applies only to GitHub-hosted verification: PR quality gates, SonarCloud, security scans and workflow checks. The applicable [PR checks](../ci/backend-pipeline.md#required-pr-checks) own that validation before merge, so these entries do not need a separate "hosted CI not checked" limitation. Evidence links retain the commands, revisions and environments actually observed; this convention does not claim an unobserved CI run passed.

Keep local-verification qualifiers for application behavior, AWS/deployment checks, provider/Sandbox tests, cross-platform compatibility and benchmarks. In mixed entries, remove only the GitHub/CI caveat and retain the other qualifications. Hosted cache-hit measurements, runtime or billing savings, known failures and accepted-risk conditions still need their own evidence; passing a PR does not establish them.
