## Timing interpretation and sources

Minute labels are aggregate start times, not individual request timestamps. Request alarm history shows the actual evaluated datapoints and query time; the 168-second post-third-minute lag is observed, not a contractual CloudWatch delay or a uniquely established ingestion fault. Subsequent 60-second cooldowns limit additional scaling but do not explain the first alarm's late evaluation. The activity duration covers ECS fulfillment; it cannot be equated with JVM boot alone. Target registration, ALB initial health, ECS deployment completion and 120-second slow start are different milestones. Earlier snapshot timestamps may precede a task API startedAt by a few seconds because the JSONL timestamp denotes collection start and calls complete asynchronously. The two-minute readiness gap makes late-task first-health times especially loose upper bounds.

Policy arbitration is governed by AWS's “largest capacity” rule when policies act concurrently, rather than summing requested changes. The fresh include-not-scaled read explains specific late request-policy no-ops but does **not** identify a CPU no-op reason; preserve that gap instead of claiming cooldown/arbitration is proved as the precise CPU outcome cause. There is no CPU action permission error in the retained alarm action, but successful action delivery is a different observation from a capacity increase.
