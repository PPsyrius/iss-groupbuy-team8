# Windows/Wi-Fi network review — 2026-11-11

**R4 remains on hold.** Existing evidence supports a load-dependent problem in a shared host/access-network path, but does not uniquely identify the Wi-Fi driver, radio, AP, gateway or WAN. No intentional traffic experiment, elevation, configuration change, container creation, repository/Git operation or sealed-evidence write was performed by this review.

## Important observations

- **Not commerce-specific:** static-only reproduction produces 11.76–13.00% request errors across default HTTP/2, forced HTTP/1.1, MTU 1400 and host-network runs; No SMPS produced 12.42%. Windows-native HTTPS controls fail alongside Docker controls, including a non-AWS destination. This excludes commerce/backend behavior and a Docker-container-only failure as sufficient explanations, not every possible Docker-induced shared-host effect.
- **Actual failing phases:** in `gateway-path-diagnostic.jsonl`, all 8 failed regional STS controls completed DNS in at most 19.261 ms but had no TCP-connect completion timestamp before the approximately 2-second deadline. Non-AWS failures comprise 4 before TCP completion, 1 after TLS/before first byte, and 3 after first byte. Neither a pure DNS failure nor a server-only response-delay theory explains the combination. The timestamps do not show whether SYNs were sent, where packets were lost, or whether the host was delayed.
- **Gateway observation, not loss localization:** the existing baseline has 0/15 gateway ICMP timeouts, static-load phase 4/20, and recovery 0/19; unrelated HTTPS controls fail 8/20 each during load. This raises the priority of the common host/radio/AP/gateway segment. A gateway ICMP timeout can also reflect ICMP deprioritization, router CPU load, scheduling or local receive delay; it does not uniquely prove a Wi-Fi or gateway packet-drop location. Probe types were sequential within each sample, not simultaneous packet measurements.
- **No spontaneous logged WLAN reset in the reviewed window:** enabled System and WLAN operational logs were queried once for 10:35–11:56 UTC. Thirty System records, four selected System WLAN records and fifteen WLAN operational records were found, without the 5,000-record cap being reached. No selected Netwtw/NDIS/TCPIP events were found. The two WLAN module stop/start and security/association sequences at approximately 11:30:22–26 and 11:33:47–51 UTC align with MIMO apply at 11:30:24 and restore at 11:33:49. Event 10002 means WLAN extensibility module stopped; it is not by itself proof of a driver crash. No event absence rules out silent RF retries, driver queueing or offload bugs.
- **Current settings, not a diagnosis:** active BE211 driver 24.70.0.3, adapter up at a 368-Mbps snapshot; Auto SMPS value 0 restored; Packet Coalescing enabled; TCP RSC enabled and operational for both families; LSO/checksum offloads enabled. TCP global output reports normal receive-window autotuning, 1,000-ms initial RTO and four SYN retransmissions. A query returned no per-adapter RSS setting object; that is not proof of an RSS fault or a reason to change it.
- **Counters cannot absolve the link:** adapter discard/error counters are zero, but ordinary NIC counters are not radio retry/airtime/802.11 loss measurements and may reset with adapter reconfiguration. One unsynchronized cumulative Windows TCP snapshot has 5,143 failed attempts and 452,726 retransmitted segments; it cannot attribute them to R3 or distinguish host/Wi-Fi/WAN. An idle snapshot with 24 TIME_WAIT and 38 established sockets against a 16,384-port dynamic range does not establish or exclude transient load-time port exhaustion.
- **Sequential control was not bandwidth-matched:** sequential HTTP/2 transfers delivered 96,186,398 bytes over about 45 seconds (17.1 Mbps) without errors. Static k6 runs received about 191.6–202.2 MB over 45 seconds plus up to 10 seconds of drain: approximately 27.9–35.9 Mbps depending on the interval. Protocol counters identify successful response protocols, not the protocol of failed handshakes. A 368–432-Mbps PHY rate is not measured usable bandwidth or spare airtime. Raw bandwidth/queueing and competing background traffic are not ruled out.
- **ALB limits:** the existing projection of 725,898 retained load-window ALB records reports 200/200 and target p95/p99/max of 9/29/945 ms. This strongly weakens slow commerce processing as the dominant explanation for the client timeouts, but successful ALB logging does not prove client receipt or account for every pre-ALB failure.

## Packet Coalescing versus RSC

Microsoft documents **NDIS Packet Coalescing** as caching selected broadcast/multicast traffic to reduce receive interrupts; unrelated/unmatched packets trigger delivery. It is not the documented mechanism that coalesces unicast TCP response segments. **Receive Segment Coalescing (RSC)** is the separate TCP receive-path feature, and it is operational here. A Packet Coalescing toggle has low mechanistic priority for these HTTPS symptoms; do not revive the cancelled elevated trial on the assumption it directly controls TCP coalescing. A vendor-specific bug remains possible but is not evidence. Intel's legacy settings page links the same Microsoft overview; it is not BE211-specific validation.

Docker Desktop's host network mode is not equivalent to moving the generator to native Windows or a separate machine: Desktop host networking is layer 4, and Docker documents outbound traffic as mediated by its backend and host networking APIs. The unsuccessful host-mode run weakens bridge/MTU explanations but does not conclusively remove Docker's shared backend/host path.

## Exact next discriminating tests — proposals only, none started

1. **Use the separately delegated diagnostic; do not overlap another load.** At aligned UTC start/end boundaries retain existing k6 connect/TLS/wait/receive summaries, offered/achieved rates, actual connection counts, and Windows active-adapter counter deltas. Preserve the native cross-destination controls and gateway observations already authorized. Treat `time_namelookup=0` as “no completion timestamp,” not a proven DNS outage. Do not extend R4's acceptance envelope to hide this issue.
2. **Read router/AP state without configuration changes — router credentials/access required, not Windows elevation.** During a bounded approved reproduction compare AP per-client retries/failed TX, airtime/channel utilization, association/DFS events, gateway CPU, queue/drop counters, NAT/session occupancy/limit and SYN-flood/security counters against idle baseline. Retain only timestamped numeric aggregates, with client identity pseudonymized; never export full router config, leases, addresses or credentials. A NAT/SYN limit increment with radio counters stable favors connection pressure; radio retries/airtime increasing without router session pressure favors the radio/AP segment. Neither is absolute proof alone.
3. **Second-device control — device owner approval required; no changes to this laptop's Wi-Fi.** During the same bounded load, have one wired device on the same gateway and, if available, another Wi-Fi device record low-rate gateway and unrelated-HTTPS controls. Only laptop fails: host/client-specific path rises. Other Wi-Fi device fails but wired succeeds: radio/AP path rises. Wired internet also fails: gateway/WAN/shared resource rises. Gateway ICMP alone still cannot decide because ICMP may be deprioritized. This generates traffic and requires fresh authorization/coordination; it was not run here.
4. **Separate concurrency from byte rate and connection churn — traffic approval required.** On a static-only fixture, compare a warmed persistent pool (for example 32 versus 1,000 actual established connections) at the same achievable request rate and response bytes; then vary new-connection rate while holding bytes/RPS as close as feasible. Pace/warm establishment separately and record actual SYN/open rate, TCP states, achieved RPS and bytes, not merely configured VUs. In k6, connections are reused per VU; HTTP/2 does not imply all VUs share one TCP connection, and `preAllocatedVUs:1000` is not proof of 1,000 simultaneously active connections. `noConnectionReuse`/`noVUConnectionReuse` change churn and must be reported. Add a low-connection download matched to the observed roughly 28–36 Mbps before claiming bandwidth is ruled out. If workload targets cannot be held, call the comparison confounded.
5. **Bounded transport/driver metadata capture — administrator/security-owner approval usually required for ETW/PktMon/WPR.** Do not start it now. Prefer aggregate TCP retransmission/SYN-retry, DPC/ISR/per-core and network-drop metadata; do not export packet payloads/endpoints. A host-side “sent” timestamp alone does not prove over-air delivery. If packet headers are necessary, agree on a private capture and sanitization/retention plan first. No firewall/EDR disablement. Existing host TCP/IP events 4227/4231, if present during a future incident, and load-time port counts can discriminate port exhaustion better than this idle snapshot.
6. **Only if evidence points to host offload: single-setting reversible RSC A/B — Windows administrator access and explicit user approval required.** Save active-adapter IPv4/IPv6 RSC states, change only the tested family's per-adapter RSC setting, repeat one static diagnostic, and restore the exact saved values immediately if ineffective or at the approved test boundary. Leave Packet Coalescing, SMPS, MTU, firewall and other offloads unchanged. Do not treat “enabled” as proof that RSC is faulty. Driver update/rollback or AP channel changes require separate maintenance approval and are not a prerequisite to try blindly before R4.
