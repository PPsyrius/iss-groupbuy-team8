## Collector integrity and tooling findings

- **Acceptance blocker, not repaired by sample coverage:** four ECS read failures at **10:49:24, 10:52:46, 10:59:01, 11:00:34 UTC** force the original observer's `collectionComplete=false`, even though retained successful samples meet the 45-second spacing rule. Supplemental failures likewise remain failures. Credentials were observed valid until **11:35:34 UTC**; these much earlier failures do not establish authentication expiry.
- **Latent analyzer integration gap:** `analyze-v3.mjs` takes four inputs but never reads `observer-result.json`; `scaling.mjs` checks successful saved observations, not failed collection attempts. A future zero-drop run could pass those narrower checks despite an incomplete collector. Require a separately source-bound collector-completeness gate in orchestration/acceptance, or explicitly extend the analyzer contract with regression coverage. Do not reinterpret `timerCompleted` as `collectionComplete` or erase errors.
- **Latent normalization integration gap:** the frozen reviewer writes then asserts `normalizationBlockers`, correctly retaining unknown/non-successful activity information; the analyzer itself does not inspect that field. Require successful normalization plus an empty blocker list before any future analyzer/acceptance decision. Current R3 has no such blockers and all three events are genuine; this is future hardening, not a new R3 rejection cause.
- **Diagnostic observability defect:** collector failures retain generic `ValueError`/AWS-operation labels rather than a safe structured distinction between transport timeout, CLI exit, AWS error code, and credential failure. Preserve redacted operation/attempt timing/exit/error-code metadata next time; never dump credential-bearing responses or full private stderr. Do not infer a cause from a generic failure alone.
- **Known curl-format defect remains separate from real transport failure:** failed curl `status:000` is invalid JSON in the original raw format; preserved process exit **28** supports **17 genuine in-load timeouts**, but unavailable timing fields cannot be reconstructed. Post-exit DNS exit **6** is outside the load window. Quoted status in inert R4 instrumentation is a collector fix, not a network remedy or permission to launch.
- **No-data is not zero:** CloudWatch `StatusCode=Complete` is API query completion, not necessarily continuous metric coverage. In particular target-5XX has zero returned points; zero filtered connection-log matches is not proof that no underlying connection problem occurred.
- **Source attribution is external by design here:** summary/preflight `testSha` alone does not identify the uncommitted policy-target binding. Retain `source-lock.json` and its verified execution hash with every claim; a future receipt should bind the complete reviewed source identity directly. Existing source hashes match, and no unchanged-committed-tooling claim is supported.

## Experimental confounds and negative cases

- Static-only **600 RPS / 1000 VUs / 45 seconds** diagnostics reproduce failure without commerce requests: default **11.758% errors / 745 drops**, forced HTTP/1 **12.999% / 1,523**, MTU1400 **12.115% / 710**, host-network **12.222% / 1,228**, gateway **12.151% / 952**, gateway No-SMPS **12.416% / 1,462**. None of these single interventions demonstrates a cure. They are short post-run diagnostics, not substitute V3 evidence or controlled repeated causal estimates.
- **Diagnostic exit zero is not a pass:** `static-concurrency.js` defines no thresholds. Read error/drop/latency metrics, not process success, when interpreting these trials. All six have substantial failures; no acceptance gate was applied or loosened by those diagnostic scripts.
- Simultaneous native/Docker controls also time out: native static **7/61**, native STS **9/61**, Docker static **7/60**, Docker STS **10/60**. A Docker-only or commerce-only explanation is insufficient, but shared host/uplink/ISP/CDN/regional paths and scheduling mean these controls cannot isolate a unique failing component.
- Conversely, sequential low-concurrency HTTP/2 and HTTP/1 static download phases recorded **418/406 transfers and zero download errors**. Preserve this negative evidence: healthy short/low-concurrency phases neither disprove concurrency-dependent failures nor validate the 30-minute application schedule. Different object sizes, connection reuse, concurrency, destination and timing remain confounds.
- Preserve the existing timing-v2 analysis: it pairs **725,925** HTTP metric batches, including one setup request, with count/hash/mean/p95 checks; zero-duration exports are retained, only empty intervals are omitted from **approximate** concurrency. Its inferred active-HTTP peak **1000** is not sampled VU peak **999**, nor proof of CPU exhaustion. Generator peak **242.95%** on eight CPUs, memory **9.98%** of 8 GiB, and no OOM do not exclude VU occupancy saturation during 10-second transport stalls. The original zero-duration assertion failure remains historical diagnostic evidence, not acceptance code.
- Spot interruption/replacement is an environmental confound, not an application-health or seven-running conclusion from these snapshots. R3 sampled a dip from six running to five and recovery; saved service events include no in-run unhealthy replacement message. Read failures mean absence of such a message is not exhaustive proof of no disruption.
- R3 request target **6000** is independent of unchanged workload knee **200**; the source and regression checks confirm the split without changing thresholds. The 30-minute offered-load schedule and peak **600 RPS** remain unchanged. Policy/slow-start/private logging changes and Spot interruption prevent a simple uncontrolled before/after attribution against prior campaigns.
- The observed growth is **1→2→3→6**, not an isolated stable four-task measurement. Neither offered RPS, six running tasks, nor passing p95 establishes the separately required **one-to-four ≥80% achieved-throughput linearity**, connection budget, final route/digest verification, dashboard evidence, or complete collector. These remain independent evidence requirements.
