# Runtime compatibility review — 2026-11-11

**NONE substantiated: the checked official release notes and upstream issue trackers do not establish a pinned k6/Go/x/net or Docker Desktop defect that explains this case's combination of high activity across approximately 1,000 established sockets and Windows-native gateway/AWS/non-AWS failures.** There are useful partial analogues, not a proven fix or a reason to upgrade the generator now. R4 remains on hold; Wi-Fi, Docker, 1,000 VUs, 600 RPS, 30 minutes and all acceptance gates remain unchanged.

## What the actual failure requires an explanation to cover

1. Approximately 1,000 established sockets alone are insufficient: 1,000 VUs/60 RPS is clean; 100 VUs/600 RPS achieves approximately 595 RPS and 37.13 Mbps with clean controls. The 1,000-VU/300-RPS and 600-RPS cases fail. Thus neither a universal 1,024-descriptor/connection limit nor a simple aggregate-throughput threshold is demonstrated; packet mix, flow activity and achieved rates remain relevant.
2. An initial SYN burst is not necessary: the supplied 30-second 60-RPS warm-up followed by 45 seconds at 600 RPS still fails 11.395%, with native failures beginning about +0.6 seconds into the high-rate phase while the original 1,000 socket inodes remain and without additional opens/SYN retransmissions in the first ten seconds. This disfavors new-dial-only and repeated-DNS-renewal explanations, not every later retry effect.
3. R3 has 8,429 failures, of which 8,426 have zero completed connect/TLS timing, with approximately 1,000 established sockets retained; the previous audit's caveat that zero timing alone does not prove reuse still applies. A stale-flow/transport stall could explain persistence, but not independently the contemporaneous native-control outage.
4. Existing native gateway ICMP timeouts and unrelated HTTPS failures require a shared-host/access-path explanation or interaction. A Linux Go HTTP deadlock alone cannot make a separately executing Windows process lose gateway ICMP replies. A generator's traffic pattern could still trigger backend/host filtering, scheduling, queue/offload or host/AP/router behavior; the responsible component is not isolated.
5. Forced HTTP/1, MTU 1400, Desktop host networking and No SMPS all failed to remove the problem. No logged spontaneous WLAN reset, enabled RSC/LSO, BE211 driver version or approximately -67 dBm RSSI identifies a culprit. Fast retained ALB target timings weaken origin-dominant blame but do not establish end-to-end delivery.

### Release-note checks that do not justify an upgrade

- [Docker Desktop release notes](https://docs.docker.com/desktop/release-notes/): installed 4.94.0 and subsequent 4.95.0–4.99.0 were checked. 4.99.0 fixes a plain-HTTP **upstream-proxy** per-request socket leak and Docker-VMM **published-port/new-connection burst** resets, neither established in this warm outbound HTTPS case. 4.96.0 fixes internal DHCP replies escaping onto the physical network; this is a real shared-network defect class, but there is no lease/address/DHCP-event evidence tying it to this rapid rate/pool transition. Do not infer missing facts by reading private proxy/settings values.
- The same Docker page documents an **old 4.43.0** host-network/then-current-WSL-kernel incompatibility and a **4.36.0** fix for an 18-open-host-port restriction. These do not establish a 4.94.0/6.18.33.2-2 approximately-1,000-active-flow regression. No old downgrade workaround is recommended. General kernel security fixes in later notes likewise are not proof of this performance symptom.
- [k6 releases API](https://api.github.com/repos/grafana/k6/releases?per_page=10): the ten returned entries span 1.7.x/1.8.x and 2.x (including a prerelease). Later v1.8.1/v2.2.0 notes describe Go **1.27** HTTP/2 negotiation/error-classification fixes, not a Go 1.25.7 established-pool/native-host failure. Browser/WebSocket teardown fixes are not this k6/http static workload. v1.8.2 dependency/security changes do not establish a matching fix. Later versions are not automatically behavior-equivalent.
- [Go release history](https://go.dev/doc/devel/release): Go 1.25.7 is documented, later maintenance contains runtime/network/security changes, and Go 1.25 is outside the stated two-newer-major support window once 1.27 is released. Support/security lifecycle is a separate maintenance concern, not proof that upgrading repairs this incident.
- Specific later fixes can be irrelevant or introduce their own constraints: [Go #80876](https://github.com/golang/go/issues/80876) is a **Go 1.25.13 server-side h2c ReadHeaderTimeout regression**, not the 1.25.7 TLS client; [Go #78833](https://github.com/golang/go/issues/78833) reports increased HPACK allocations **after x/net v0.49.0 → v0.53.0**, not a v0.49.0 native-network outage. Neither supports “upgrade x/net to fix it.”
- [Docker's networking documentation](https://docs.docker.com/desktop/features/networking/) describes Windows outbound container traffic going through `com.docker.backend`, which creates host TCP/IP connections. [Desktop host networking](https://docs.docker.com/engine/network/drivers/host/#docker-desktop) is layer 4 and does not grant direct host-interface access. The unsuccessful host-network trial therefore does **not** bypass all Desktop/backend/Windows paths or prove Docker innocent.

## Recommendations and later comparative-version criteria

1. **Now — high confidence:** keep every pin and acceptance gate unchanged, add no test traffic, and wait for the independently authorized active-100/held-1,000 discriminator. This review neither authorizes R4 nor treats a static-only success as backend promotion. The strongest supported description remains **high activity × large established pool interacting with a shared host/access path; component unresolved**.
2. **Interpret that discriminator, do not assume its outcome:** clean 100-active with 1,000 truly retained sockets at comparable achieved RPS/bytes would weaken occupancy-only limits/leaks and prioritize the number of recently active flows; failure would keep occupancy/shared per-flow resources in play. Neither result alone identifies Go, Desktop, Wi-Fi/AP or router. Account for which sockets really remained established and active; VU count is not a socket-activity measurement.
3. **Evidence gate for a Desktop-version A/B — conditional, not recommended as an immediate fix:** a later approved bounded diagnostic would need a specific new signature, such as aged Bound growth/port allocation errors corresponding to #769/#781, backend-stack/counter evidence, or DHCP anomalies corresponding to the 4.96.0 fix. Capture only sanitized aggregate metadata in a separately authorized scope. There is no reason from the checked notes to prescribe 4.99.0, a kernel downgrade, a proxy change or routine restarts as the cure. Backend-mediated traffic can trigger host/offload/queue pathology without any Go HTTP implementation error.
4. **Generator-version comparison — later falsification is defensible, adoption is not yet justified:** if native failures remain reproducible specifically with the many-active-flow k6 pattern after the discriminator, an explicitly authorized static-only A/B/A using the locked image and one separately pinned official candidate can test whether the **generator bundle/traffic shape** changes the trigger. A maintained v1 line is a lower migration-confound candidate than v2, but no candidate version/digest is selected or approved here. Hold Desktop/WSL, Wi-Fi/driver, target, source/options, timeout/reuse/protocol, actual warm-pool size, offered/achieved rates and bytes as constant as possible; retain native-control outcomes and aggregate actual opens/active-flow observations. If wire shape/protocol or achieved load changes, label the comparison confounded, not fixed. No image was pulled or changed.
5. **To claim Go or x/net specifically — higher bar:** the above multi-dependency image comparison cannot isolate the compiler/runtime. A separately authorized, provenance-reviewed matched-build pair would need the same k6 source/options/dependency lock with only Go changed, or only x/net changed in a separate comparison, plus a matched old-toolchain rebuild that first reproduces the official-image behavior. Even the baseline rebuild is a separate variant because packaged-source equivalence is not proven by the dirty marker. Review compatibility and any changed HTTP/2 delegation/error classification before interpreting results. No build, library upgrade or runtime flag experiment is performed or prescribed as remediation here.
6. **Pin/review any future variant separately:** record immutable image digest/platform, binary SHA-256 and parsed Go build info (actual compiler, module/dependency revisions, VCS modified flag), source/workload/adapter hashes, output schema and timeout/reuse/DNS/transport semantics. Assign a new diagnostic variant ID and retain original R3/pin unchanged. A clean comparator would show only a potential generator/environment mitigation under that diagnostic, not a demonstrated defect fix or backend improvement. Promotion would require explicit review and a new full 1,000-VU/600-RPS/30-minute campaign with unchanged gates after all blocking issues are isolated.

- **High:** no checked source supplies the required matching mechanism plus affected/current/fixed version proof; no library/image upgrade is justified as this incident's fix; Linux-only HTTP failure cannot independently explain native gateway ICMP loss.
- **Moderate:** Desktop mediation and a large-active-pool shared-path interaction remain plausible; the documented silent-HTTP/2-flow behavior is a plausible persistence/amplification mechanism, not a demonstrated original trigger.
