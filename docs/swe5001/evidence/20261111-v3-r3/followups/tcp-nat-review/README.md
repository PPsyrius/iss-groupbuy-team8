# TCP/NAT/queue/host-scheduling review

**R4 remains HARD HOLD. No new load, connectivity probe, AWS call, host setting change or validated fix.** Existing failing-load samples provide no evidence of Linux TCP memory pressure, socket-queue drops or TIME_WAIT exhaustion. Present-time Linux conntrack and Windows port capacity are far from exhaustion, but this passive interval did not overlap the sole traffic agent's case and cannot exclude transient load-time faults in Windows, Docker forwarding, driver queues, WFP, Wi-Fi/AP, or router NAT.

## Important update to the initial hypothesis

The completed [warm-establishment case](../rate-concurrency-review/warm-establishment/README.md) changes the older matrix interpretation: the high-rate phase failed with all 1000 warmed sockets retained and no additional opens/SYN retransmits in its early samples; native failures began before later reconnects. Initial SYN/establishment bursts are therefore **not necessary** for the disruption. A router flow/session-processing problem remains possible, but a pure new-SYN-rate threshold is no longer the strongest general explanation. This review does not duplicate the other agent's VU/lifecycle analysis or rerun that case.

### TCP aborts are not automatic evidence of a resource ceiling

The failing cold matrix case has `TCPAbortOnData` rising 0→73 while `TCPAbortOnMemory`, `TCPAbortOnTimeout`, `TCPAbortOnClose`, `TCPAbortOnLinger` and `TCPAbortFailed` stay zero; the warm case has `TCPAbortOnData` 0→1. An abort-on-data counter can reflect socket-close/reset behavior around unread data; it neither identifies the cause of the application's ten-second timeout nor demonstrates memory exhaustion, router rejection or intentional firewall blocking. `TCPTimeouts`/`TCPSynRetrans` count transport retransmission timers, not k6 request-timeout events, so their counts need not equal application errors.

## Passive interval: attribution and limitations

- Linux: **2026-11-11 12:24:55.553Z–12:25:55.550Z**, 13 samples spaced five seconds apart, approximately 59.997 seconds between first and last reads; Windows: **12:24:54.964Z–12:25:54.959Z**, also 13 samples. Controller setup/teardown spans 12:24:48.755Z–12:25:56.307Z; the receipt's 61.34-second stopwatch includes last-sample processing and joining the job, not a second monitoring interval. No repeat interval was collected.
- The authorized warm load ended around **12:14:43Z**, roughly ten minutes earlier. This interval is **post-load/no target-case overlap**, not proof of a healthy load path. There is background activity: Windows cumulative IPv4 connection failures increase **5568→5579** and IPv6 **421→422**, while the sampled TCPv4 retransmit rate is zero. No destination/process attribution was collected, so these failures cannot be assigned to k6, Wi-Fi, Docker, or the prior case. This is not a pristine zero-error idle control.
- Linux host namespace TCP active opens/failures/retransmit totals do not change during this interval, while conntrack entries increase. Local TCP counters and forwarding/conntrack accounting cover different scopes; do not infer that the entire machine or forwarding path was inactive.
- Three sysctls are not exposed in this view: `net/core/netdev_max_backlog`, `net/ipv4/tcp_mem`, and `net/ipv4/tcp_max_orphans`, each `FileNotFoundError`, errno 2. This is missing observability, not a zero-valued setting. No collection permission denial occurred; Windows counter statuses were valid. `collection-errors.json` is an explicit empty array; it was materialized offline because the collector's original empty-array pipeline emitted no file. The collector was subsequently corrected only to serialize empty arrays, without recollection.
- `/proc/net/softnet_stat` is numeric host-kernel metadata; its current cumulative zeros/unchanged squeeze count cannot establish historical packet-processing timing. Linux conntrack and sysctls were read with a temporary cached Python container using `--network host --read-only --cap-drop ALL --security-opt no-new-privileges`, 0.25 CPU/128 MiB, no host mounts, no privileged mode and no process/environment/command-line access. Host networking here does not expose the physical router or make Docker Desktop equivalent to native Windows.

## Exact missing observability

1. **During the failing phase:** Linux host conntrack occupancy/failure deltas and softnet counters, Windows TCP state/port occupancy, cumulative failed-open deltas, per-core DPC/ISR/interrupt/CPU counters, Windows allocation failures and memory/nonpaged-pool trend. Existing current-time metadata cannot reconstruct these values retroactively.
2. **Windows/Docker path:** packet/queue/drop accounting at Desktop backend, Windows NAT/virtual switch, NIC and WFP callout layers, with provider/category attribution and no endpoint/payload export. A loaded `WinNat` service does not establish that its table carries the diagnostic traffic. Full WFP exports/ETW/PktMon were not attempted because they exceed this scope.
3. **Router/AP:** actual NAT/session occupancy and ceiling, allocation/insertion failures, SYN/security rejection counters, gateway CPU and queue/drop counts, per-client radio retry/failure/airtime counters. Linux `nf_conntrack_max` is not a proxy for any of these. Router/AP access is unavailable; no credentials were sought, LAN scan performed or admin endpoint contacted.

## Most discriminating next test — proposal only

**The next traffic experiment, if separately approved, should be a single static-only warmed-pool case on the same Windows/Docker machine over an already-available authorized wired path, with Wi-Fi left unchanged and no concurrent load.** Keep pinned image, 1000 VUs, achieved request rate/response bytes, warm-pool establishment, timeout and duration comparable; record actual transport-pool retention rather than configured VUs. Collect the passive Windows per-core/DPC/ISR/ports/failures and Linux conntrack/softnet counter streams synchronously from baseline through recovery. This is a network-path substitution experiment, not an offload/security/MTU tuning experiment, and requires fresh traffic/network authorization and a suitable wired connection; nothing was started here.

- If the symptom disappears on wired at comparable delivered workload while the same host/container/filter stack is retained, the Wi-Fi/client-radio/AP branch rises; this still does not distinguish client driver from AP or prove a fix for V3.
- If it persists with stable Linux conntrack and port budget, Windows/backend/filter/shared-router/WAN processing remains; failure-time DPC saturation or conntrack insertion/drop increments would materially sharpen the next branch. A wired result at much lower delivered traffic is confounded and cannot be called a pass.
- If a path substitution is unavailable, the most valuable instrumentation addition to **one already-authorized future case** is synchronized load-time counters plus router/AP numeric telemetry obtained by its owner, not another repetition of the completed warm/SYN or MTU/host-network cases. Without router counters, report NAT/session-capacity as **not excluded, not demonstrated**.

No hypothesis is a validated mitigation. Packet Coalescing is not TCP RSC; no arbitrary knob recommendation is made. All V3/R4 acceptance requirements remain unchanged.
