## Code review of the exercised released read path (`93984f61`)

- `ProductController.java:70–83`: the driver supplies no keyword/AI flag and performs only catalogue list/detail GETs. These delegate to the ordinary catalogue service, not semantic ranking or payment/identity operations.
- `ProductAppServiceImpl.java:55–60,115–124,142–149`: product reads use a short read-only transaction and return the JDBC connection before the Redis-backed deal lookup. The old “Redis holds the product transaction open” explanation does not match this source.
- `ProductRepositoryImpl.java:131–137` and `BizProductMapper.xml:173–186`: list uses two bounded SQL queries; detail uses one product lookup. `GroupDealQueryServiceImpl.java:44–64` batches deal-cache reads and database misses; no per-product SQL loop was found on this path.
- `RedisOpenDealOfferCache.java:59–78,101–121`: Redis reads use MGET and population is a batch Lua call. Redis unavailability falls back to PostgreSQL; there are no cache-hit/miss/latency measurements in the archive to establish whether this occurred.
- `ProductConverter.java:18–19,85–93` reuses a static JSON mapper; it does not construct an object mapper per product. List reads still hydrate full products and parse images before returning summaries: a profiling candidate, not an established hot spot or approved optimization.
- `ecs-service/main.tf:149–155` probes the shared `/api/actuator/health` endpoint. The retained data does not establish whether the unhealthy event came from CPU/queue delay, database/Redis health or a different failure. Do not weaken the probe merely to stop replacements.
