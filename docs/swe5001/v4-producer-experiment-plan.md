## Producer design and source verification

The expiry design belongs to [backend ADR 0002](../../backend/docs/adr/0002-team-lifecycle-events.md). Default shard count one must retain the original `team-expiry-sweep` lease and unfiltered candidate query. An explicitly configured count **1..6** may select one deterministic shard per timer invocation, with at most 500 candidates, followed by the existing sequential independently transactional `expireOne` calls. Retry/backoff retains its logical key. No per-team asynchronous database work, new pool or changed team → intent → order → payment lock order is permitted. At count six the new envelope is at most six shard batches / 3,000 selected candidates, not six batches secretly processed by one invocation. Lease-loss overlap and aggregate idempotency backstops remain explicit limitations.

The actual Spring property is `blocbuy.scheduling.team-expiry.sharding.count`, bound by `BLOCBUY_SCHEDULING_TEAMEXPIRY_SHARDING_COUNT`; the earlier proposed `BLOCBUY_SCHEDULING_TEAM_EXPIRY_SHARD_COUNT` is not that binding. Normal Terraform omits this key. The corrected exact source passed 46 network-disabled mocked-provider tests at 00:58 SGT; the prior wrong-key proof remains historical, not proof of this corrected configuration.

The separately prepared SNS transport candidate defaults to concurrency one and the relay to PT2S. Its synthetic transport benchmark is not an AWS or end-to-end expiry benchmark. Enable different pacing only when the combined producer experiment and actual rate evidence justify it; do not attribute the observed expiry bottleneck to the SNS relay.

Require JDK 21, full Docker-backed Maven verification, architecture/static gates and the authoritative JaCoCo aggregate before packaging; new/changed code must meet the existing **≥80% new-code** requirement. Add real PostgreSQL partition, retry/deleted/deadline/order/limit, lease, settlement-race, rollback, terminal-event and refund-idempotency tests before cloud use. Local scan plans and concurrency benchmarks must report their environment and limits, without promising a sixfold speedup.

Local expiry ABBA measurements were 225/225 events per second single-flight and 634/688 with six shards, aggregate 2.934×, in one JVM sharing five connections with mocked gateways. A separate PostgreSQL 18 scan benchmark included 62,000 closed historical rows in each dataset: at 80,000 open rows, shard median/max were 8.570/9.097 ms; all 63 measured queries returned 500 and wrote no temporary blocks. Shards still scan the due-candidate set before filtering, rather than reading an indexed sixth; warm sequential local scans are not an AWS throughput or consumer-ceiling guarantee.
