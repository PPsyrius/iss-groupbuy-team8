# Invite reference cache (#276, #208 phase 3)

`ShareInviteRepository.findByRef` is shared by JOIN attribution and the anonymous invite landing page. The infrastructure repository wrapper caches only a well-formed, existing `inviteRef → ShareInvite` lookup; PostgreSQL remains authoritative. The wrapper leaves the domain port, application services, HTTP routes, response shapes, and the other repository operations unchanged. Its source query joins the deal row only to obtain `expire_time` in the same PostgreSQL read; a missing deal deadline makes the value uncacheable without changing the invite result.

| Owner | Key | Value | TTL | Cardinality |
| --- | --- | --- | --- | --- |
| Groupbuy infrastructure | `blocbuy:{env}:groupbuy:invite-ref:{ref}` | Versioned JSON containing invite IDs/ref and deal deadline | Random 20–30 seconds, capped by remaining time until `biz_group_deal.expire_time` | At most one key per distinct valid reference read in the last 30 seconds |

Only positive lookups are cached. Missing or malformed references never create keys, so a later insert is visible on the next read. Each write supplies an explicit Redis TTL. A changed/deleted invite may remain visible for at most 30 seconds while its key is warm; there is currently no invite mutation/deletion route requiring immediate invalidation. If one is added, it must evict this key after commit before promising immediate visibility. The key contains an opaque random reference, not a user ID, quote, payment detail, or credential. Values are server-side only and the public response still carries `Cache-Control: no-store`.

An unsupported/malformed payload, reference mismatch, expired deadline, Redis read failure, or cache miss falls back to the original PostgreSQL lookup. Write failure preserves that result. A read outage skips a second Redis write attempt on the same request. Redis never decides whether a buyer may join: deal identity, self-referral and paid-seat admission continue through the existing application checks and PostgreSQL locks. This cache adds no new database transaction or remote call inside the seat-admission lock. It also does not claim availability of Redis-backed authentication during a shared Redis outage.

`RedisCachedShareInviteRepositoryTest` covers warm hits, bounded TTLs, malformed/foreign/expired entries, missing references, delegation and Redis read/write failures. `InviteRefCacheIT` uses real PostgreSQL and Redis to prove that repeated JOIN attribution and public resolve share the key, expiry reloads the current database row, near-deadline TTL does not extend the deal lifetime, and ended/missing invitations still follow the existing PostgreSQL behavior. This is functional cache evidence, not a measured latency claim. The full backend verification retains existing settlement, referral and concurrency tests.
