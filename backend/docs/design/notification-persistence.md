# Notification persistence and read API (#215)

Date: 2026-10-13. Implements the agreed, reduced scope in [#215's October 11 comments](https://github.com/PPsyrius/iss-groupbuy-team8/issues/215#issuecomment-6110253432), under [ADR 0007](../adr/0007-cross-service-events-sns-sqs.md).

## Use case and boundaries

One immutable in-app notification per recipient for `TeamSucceeded`, `TeamExpired` or `PaymentSucceeded`. Commerce resolves recipients; #446 validates the integration envelope and renders bounded plain-text title/content. Team events reference a team ID; payment events reference a payment ID. This issue adds no listener, publisher, unread state, mark-as-read, external delivery or frontend bell.

`Notification` owns non-null identities/type/time and non-blank title/content limits (128/1024 Java characters). `NotificationAppService.recordBatch` accepts 1–1000 validated effects, generates no remote calls and performs one SQL batch inside a REQUIRED local transaction. The caller supplies UUIDv7 row IDs (`UuidV7.next()`), the envelope `eventId` and server creation time, never client-controlled identity or text.

`NotificationRepository.insertIfAbsent` retains the first effect for `(event_id, user_id)`; replay is a no-op even if the incoming row ID differs. The unique key includes soft-deleted rows, so replay never resurrects deleted effects. There is no mutable command or optimistic version in this scope. #446 must insert its `(eventId, consumer)` marker and these effects in the same transaction and acknowledge only after commit; the repository uniqueness is a defensive second boundary, not a replacement for consumer idempotency.

## HTTP contract

`GET /api/v1/notifications?page=1&size=20` requires a Sa-Token login and returns a `Result<PageResult<NotificationResponse>>`. Size is 1–100, page is at least 1, order is `create_time DESC, id DESC`; only the session recipient's active rows are queried. Each item exposes `id`, `type`, `referenceId`, `title`, `content`, `createTime`, never recipient IDs, event IDs or audit actors. Responses use `Cache-Control: no-store`. Render title/content as plain text, not HTML.

Page and count run in one read-only REPEATABLE READ transaction (3 s timeout). Offset paging matches existing APIs and can shift across requests when notifications arrive; it is not a cursor or a stable multi-request snapshot. There are no object lookup or write endpoints.

## Consumed-message ledger (#446)

V28 creates `sys_consumed_message (event_id, consumer, consumed_at)` with primary key `pk_sys_consumed_message (event_id, consumer)`; [canonical SQL](../db/notification.sql). It is an immutable system log, so it carries no surrogate ID, audit actors or soft-delete flag: deleting a marker would re-enable replay. The domain port `ConsumedMessageRepository.markConsumed(eventId, consumer)` runs `INSERT ... ON CONFLICT DO NOTHING` and returns `true` only when it inserted the marker. The consumer calls it first inside the transaction that records the notifications; `false` means the event was already applied, so it writes nothing and acknowledges the message. Concurrent first deliveries serialize on the primary key, and a rolled-back transaction leaves the event unconsumed. `afterMigrate__service_grants.sql` already assigns the table to notification. No retention job is added; rows are small and must outlive SQS retention plus any DLQ redrive.

## Event handling (#446)

Layering: the application module has no Jackson dependency and the infrastructure module may not depend on the application module, so the work is split along the existing port pattern. `IntegrationEventDecoder` (infrastructure, `com.blocbuy.notification.messaging`) is the anti-corruption layer: it reads the body as a JSON tree, checks `eventType` and `version` against the supported set (`TeamSucceeded`, `TeamExpired`, `PaymentSucceeded`, all version 1), and only then binds the `*V1` contract from `blocbuy-client` and translates it into the domain `NotificationEvent`. An unsupported pair, such as the `messaging-check.sh` probe with `version=2147483647` and an empty payload, is reported as unsupported so the consumer acknowledges it without effect. Anything that cannot be bound (not JSON, missing or non-integer envelope fields, a payload that violates its contract) raises `MalformedIntegrationEventException`, whose message names the failed check and, for binding failures, the field path (for example `payload.recipientUserIds[0]`) but never echoes payload values; a supported `eventType` with a version below 1 is malformed too, because every contract version starts at 1; the consumer leaves such a message for redrive to the DLQ. Unknown JSON fields are ignored so contracts can evolve additively.

`NotificationEventHandler` is an inbound port in the domain (`com.blocbuy.notification.event`), implemented by `NotificationEventAppService`; the domain is the only module both infrastructure and application see, and the `event` package is framework-free and guarded by ArchUnit's `domain_is_framework_free` rule, so the port carries only JDK and domain types. One `@Transactional(timeout = 10)` call renders the notifications (`NotificationEventAssembler`, fixed plain-text wording, no names or amounts), inserts the `(eventId, consumer)` marker and, when the marker is new, calls `recordBatch` in chunks of at most 1000 rows; `recordBatch` joins the transaction. It returns `APPLIED` or `DUPLICATE`; any exception rolls back both the marker and the notifications, so the message is redelivered. Team events reference the team (`dealId`); payment events reference the payment, with separate wording for `START` and `JOIN`.

Empty recipient list: commerce resolves recipients before publishing, so an empty list is a valid fact with nobody to tell, not poison. The handler marks the event consumed, writes no notification, logs a WARN with the eventId and type, and returns `APPLIED`; redelivery is then a cheap `DUPLICATE`. Duplicate recipient IDs are collapsed in their original order.

## SQS consumer (#446)

`SqsNotificationEventConsumer` (infrastructure, `com.blocbuy.notification.messaging`) is an AWS SDK v2 long-poll loop, because Spring Cloud AWS has no Spring Boot 4.1 line. It is assembled by `NotificationConsumerConfiguration` only when `blocbuy.events.consumer.enabled=true`; the package is scanned by the monolith and notification-svc, never by commerce-svc or identity-svc. It owns its `SqsClient` (attempt timeout wait + 10 s, call timeout wait + 25 s) instead of reusing the relay's 15 s client or publishing a second `SqsClient` bean, and reads the queue URL, Region and endpoint from `blocbuy.events.*`.

One poller thread acquires a free-worker permit before every receive and asks for at most as many messages as there are free workers (`concurrency`, default 4; at most 10 per call), so nothing waits in memory and a slow database applies back-pressure to SQS. Each receive requests the 20 s wait, a 60 s visibility timeout (set explicitly; ElasticMQ's queue default is 30 s), `ApproximateReceiveCount` and all message attributes. A worker restores `traceId` into MDC from the message attribute (the `TraceIdFilter` rule: 1-64 characters, each `Character.isLetterOrDigit` or `-`, `_`, `.`), otherwise from the envelope, otherwise a new one, and clears it afterwards; poller and lifecycle log lines carry no trace ID. `wait-time` and `visibility-timeout` are whole seconds and the wait is at least 1 s, so empty receives cannot spin.

| Outcome | Action |
|---|---|
| `APPLIED`, `DUPLICATE` (handler committed) | delete |
| unsupported `eventType`/`version` | WARN, delete, no effect |
| `MalformedIntegrationEventException` | WARN with messageId, eventId, receiveCount and reason; not deleted |
| any other exception (database, timeout) | WARN with messageId, receiveCount, eventId and eventType (when decoded) and the exception; not deleted |
| delete fails after commit | WARN; redelivery is a `DUPLICATE` |

Undeleted messages reappear after the visibility timeout, so failures never hot-loop; after five receives the queue's redrive policy moves them to the DLQ. Logs carry IDs and the failed check only, never payload values. `SmartLifecycle.stop` sets the stop flag without interrupting the poller (an interrupted AWS SDK call is aborted when its response arrives, and so would be a release made on that thread), lets in-flight messages finish for up to `shutdown-timeout` (15 s), then makes the unfinished ones visible again with `ChangeMessageVisibility(0)` and waits up to 3 s more for the interrupted workers. A long poll still open at stop is left to return: the poller then makes everything it received visible again at once and exits, so no receive attempt is wasted. `destroy()` waits up to 2 s for the poller before closing the client; closing aborts a long poll that is still open, and anything that call received reappears after the visibility timeout. Shutdown is sequential: this consumer's lifecycle phase (up to 15 s plus 3 s) runs first, then the web server's graceful shutdown, then bean destruction, where the task scheduler waits up to 20 s and the consumer up to 2 s for its poller. In the worst case the total exceeds the 30 s Compose `stop_grace_period`; the process is then killed and in-flight messages reappear after the visibility timeout. Idempotency makes every redelivery safe.

ElasticMQ integration tests in the monolith context cover the acceptance criteria: one envelope sent three times creates one notification per recipient and one ledger row; a malformed `PaymentSucceeded` is decoded five times and then found in `notification-events-dlq` while valid messages sent alongside are applied; a `version=2147483647` probe is deleted without effect. Only the poison test counts decodes exactly (5); the duplicate and probe tests count at least 3 and at least 1, because the 1 s test visibility may redeliver a copy on a slow runner, and they prove deletion by a drained queue (no visible and no in-flight messages).
